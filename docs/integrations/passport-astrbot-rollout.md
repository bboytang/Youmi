# Passport 发布、验收与回退操作方案

状态：待执行。以通过 GitHub Actions 的精确提交和实际生产清单为准；本文不是部署或设备验收记录。有关范围、进度见 [方案](passport-astrbot-plan.md) 和 [工作记录](passport-astrbot-worklog.md)。

## 发布前核对

1. 核对实际主机、Compose 文件顺序、当前语音/Manager/AstrBot 镜像或 JAR、插件版本、挂载及容器健康状态；记录不可变镜像 ID、候选提交、Actions 链接和运行证据。不要打印服务凭据、模型密钥或聊天正文。
2. 确认当前数据库迁移表 `mia_schema_migrations` 的版本和校验，执行 SQLite `quick_check`，检查该 owner 及 Passport 真实设备的授权和绑定，确认 QQ 使用同一 owner。检查设备使用的现有协议与连接；只读检查不等于设备已通过语音验收。
3. 在隔离副本或全新临时数据库验证 V18→V19 升级、幂等重启及校验失败回滚；核对原有记忆、情绪、角色及音色仍可读取。用户此前取消新增生产备份，不得把现有卷或镜像称作新备份。
4. 根据实际生产版本验证 Manager 补丁与原 JAR 的兼容性，并使用保留原 JAR 其他条目的构建方案；核对服务端安装制品包含 V19、共享历史、Passport 模块。确认没有其他实例会用旧迁移加载器并发访问该数据库。
5. 在生产变更前确认语音服务使用 V19-aware 候选，设备列表默认 `[]`，AstrBot 的 `passport_enabled` 默认 `false`。记录旧镜像及配置的准确标识和现有数据卷，不使用 `down -v`。

## 受控启用与验收

1. 按现有运维部署流程部署已验证的 Manager、语音服务和 AstrBot 插件；保持两个开关关闭，确认健康、原 QQ 文字/语音、角色、记忆和情绪行为正常。确认实际迁移版本为 19、SQLite `quick_check` 成功且原有数据仍可读。
2. 先启动 AstrBot Passport 消费者，再仅将已经核验的实体设备 ID 加入语音服务环境变量 `YOUMI_PASSPORT_ASTRBOT_DEVICES` 的 JSON 数组。使用实际配置机制使变更生效并核验设备重新连接；不得通过伪造 QQ 或设备 Scope 测试。开启消费者但设备列表为空时设备仍使用原路径。
3. 用户在 QQ 和设备间交替发起无敏感信息的真实对话，验证两个方向的最近已完成话题衔接；并发对话应只共享已完成回合。检查一次发送、一次完成及记忆/情绪效果，避免记录对话正文。
4. 设备真实验证语音识别、播放、连续对话、中断、断网重连、Agent 工具和设备 MCP；对设备不可展示的内容验证文字回退。QQ 原有插件和文本/语音回归。记录实际动作和用户反馈，发送到 TTS 队列不等于设备播放成功。
5. 验证“这段别记”、暂停、恢复、清除和到期行为；核对清除仅影响共享历史和摘要。验证断权、重复、超时及工具动作结果不确定时不重放。记录无法实测的项目，不将 fixture 等同实机。

## 故障降级与回退

- 首先从 `YOUMI_PASSPORT_ASTRBOT_DEVICES` 移除目标设备，按实际部署方式使配置生效；新设备回合回到原有语音路径。再关闭 AstrBot `passport_enabled` 并按原流程重新加载。已在途回合可能失败或被中断，不重放设备动作。核对 QQ 和设备的原链路恢复。
- 如需要停止跨端记录，使用有权限的“暂停跨设备对话共享”；确认暂停后不再写入共享历史。暂停与清除不同，不应擅自清除数据或原有长期记忆。
- **不能**把未识别 V19 的旧服务直接接回已迁移数据库；旧加载器会拒绝未知迁移。优先保留 V19-aware 服务并关闭入口。若确需退回旧代码，必须先单独设计并验证兼容运行版本和数据迁移方案，确认不会丢失用户记录后再执行；现有测试没有证明可直接降库。
- 如在途请求曾执行设备工具但未收到结果，状态为不确定，人工核验设备状态，不自动重试。记录故障时间、组件版本、具体检查和用户反馈，避免记录隐私正文。
